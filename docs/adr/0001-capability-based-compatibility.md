# 采用能力探测与尽力数据保护的兼容策略

## Context

通知流转设置面板依赖 `com.miui.voiceassist` 的内部类和规则存储，当前已知基线为 `8.2.70.8421`。这些接口可能被混淆，也可能在签名不变时改变语义。严格的已测版本白名单能提供更强的写入保证，但会导致每次 VoiceAssist 更新后都无法写入，直到模块重新验收。

用户选择 Q9 的 B 方案：以运行时能力探测替代已测版本白名单，并通过串行写入、快照、回读校验和尽力回滚控制风险。

## Decision

只要关键能力探测通过，并具备规则与权限的安全快照，未知 VoiceAssist 版本也允许读取和写入规则。

1. 探测关键类、构造器、方法签名、字段、状态值、规则 DSL 结构和序列化解析能力；探测不通过时进入只读或不可用状态。
2. 每次写入前保存完整 last-known-good 快照，包含所有规则、`ruleId`、筛选条件、状态和权限信息。
3. 写入必须串行化，一次只允许一个规则操作。
4. 不自动迁移、不自动规范化、不清理未知字段。
5. 写入后重新读取 store 和实际规则文件，校验目标规则、未修改规则、规则数量、`ruleId` 唯一性及 DSL 结构。
6. 检测到可验证的结构性失败时停止写入，并尽力通过 store API 回滚；无法验证回滚结果时进入只读故障态。
7. 未知版本必须在 UI 中标记“兼容性未经完整验收”，不得宣称已完全兼容。
8. 默认最多重试一次，且重试前必须重新读取并验证当前状态。高级调试开关可允许用户无条件继续发起手动重试，但它只取消重试次数上限和重试前验证，不保证写入成功，也不能覆盖首次写入前的 LKG 快照；开关在操作周期结束、页面退出或进程重启后自动关闭。

## Accepted Risks

用户明确接受以下残余风险：

- 同名方法语义变化可能无法通过能力探测发现。
- 规则结构合法但发送行为错误时，可能不会触发回滚。
- 错误通知一旦发出，数据回滚无法撤回已传输内容。
- 快照和回滚只能覆盖可检测的结构性问题，不能保证已有规则在语义上绝对完好。
- 调试模式下跳过重试前状态验证，可能覆盖或放大已经存在的异常结构；系统只能保证允许继续发起重试，不能保证重试成功。
- 因此，本方案的数据安全保证不等同于 Q9 A 的“已测版本白名单 + 能力探测”方案。

## Considered Options

- **Q9 A：已测版本白名单 + 能力探测。** 安全性更高，但每次目标应用升级都可能阻断写入。
- **Q9 C：严格版本号匹配。** 未知版本连读取都禁用，可用性过低。
- **Q9 D：仅捕获异常。** 可能在失败前写入部分状态，无法满足基本数据保护要求。

## Consequences

- 模块必须维护一套明确的能力探测和回读校验逻辑，不能只依赖反射调用成功。
- 写入路径比普通 CRUD 更重，但必须保持串行和可回滚。
- 面对未知版本，产品文案必须区分“能力探测通过”和“已完整验收”，不能把前者描述成后者。
- `NotificationSubscriptionStore` 使用 `ignoreUnknownKeys=true`，且每次写盘都会重序列化完整规则列表。当前版本必须先检测整份原始规则文件中是否存在无法表达的字段或结构；一旦存在就禁止写入。通过 hook 上游序列化逻辑以保留其他规则未知字段属于后续增强，不是首版实现目标。
