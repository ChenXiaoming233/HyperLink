## 一、一页速览

```
用户说话 → 小爱 LLM 生成规则 JSON → 手机弹窗授权 → 写入两条 JSON
                                                        ↓
非系统通知 → 小爱 NotificationForwardListener → 五道闸门判定
                                                        ↓
                        A2A 封装(notif.forward) → Continuity 直连(channels=2)
                                                        ↓
                              电脑/平板小爱 NotifForwardRpcHandler → 系统通知
```

**关键定性**：这是「智能体委托」，不是「通知镜像」。手机小爱把一条通知作为事件**派发**给对端小爱，对端小爱用自己的方式在本地呈现，不是逐像素复制。因此 PC 端出现的是**由电脑小爱生成的系统通知**，而非手机通知的投影。

## 二、两套并行系统（v3 最重要结论）

| 维度 | **小爱 A2A（实际生效）** | **MiLink NotificationTrans（发送侧未承载）** |
|---|---|---|
| 宿主 | `com.miui.voiceassist`（特权应用） | `com.milink.service` |
| 核心类 | `NotificationForwardListener` | `NotifTransListenerService` |
| 传输服务 | `A2AStaticTopicService`（topic `assistantA2a`） | `NotificationTransService`（topic `notifi_trans`） |
| 设备标识 | 账号 suid `v1:4:pc_xxx` + lyra id 双映射 | 仅 lyra id |
| 规则存储 | `notification-subscriptions.json`（**3 条已启用**） | `app_list_prefs.xml`（**无应用条目，仅协议版本**） |
| 接收侧配置 | — | `receive_app_list_prefs.xml`：小米 13 Ultra（`C48CCF92`）5 个应用，`deviceSwitch=1` |
| 授权存储 | `notification-forward-permissions.json`（3 台 granted） | 无 |
| 通知监听状态 | ✅ 已授权且 live | ❌ 发送侧监听未授权、未绑定 |
| 传输实绩 | ✅ 有 `notif.forward` 调用 | ❌ 未发现 `trans/notify` 调用（服务有绑定记录） |

**结论**：文档 v1/v2 描述的「manage_notification 工具」属于小爱这一套。小爱 A2A 是当前手机→平板/PC 通知流转的实际链路；MiLink **发送侧**未承载该链路，但**接收侧**已为 小米 13 Ultra（`C48CCF92`）配置，不能笼统说 MiLink「从未被配置过」。

**功能分工（小爱侧已有代码支持）**：小爱 `isLegalReceiver` 只接受 `PC` / `PAD` / `MAC`，`validateReceiver` 明确拒绝手机作为接收端；`ManageNotificationTool.execute` 在 Pad 本机也会直接拦截。由此可确认手机→平板/PC 归小爱 A2A。手机-小米手机由 MiLink 承担，与设置页入口及 MiLink 接收侧配置一致；iPhone 是否同路由 MiLink 尚未验证。本轮先聚焦手机-平板/PC，MiLink 手机-手机链路暂不继续探查。MiLink 另有 `mirror_notification=true`，属于通知镜像，不能直接等同于 `NotificationTrans`。

## 四、A2A 是什么

**Agent-to-Agent**，超级小爱跨设备的智能体通信层。

```
com.aios.osbot.a2a.discovery.*     A2aAgentCard / A2aRemoteManifest
com.aios.osbot.a2a.index.*         A2aAgentIndex / A2aAgentIndexManager
com.aios.osbot.a2a.runtime.*       A2aAgentExecutor / A2aRoute / A2aStreamAggregator
com.aios.osbot.interconnect.transport.continuity.*   A2AStaticTopicService
```

设备间先交换 **Agent Profile**（能做什么），再按需派任务。Profile 示例（✅实测）：

```json
{
  "name": "miclaw1.0", "version": 1,
  "capabilities": {"streaming": true, "extensions": [{
      "uri": "urn:miclaw:a2a",
      "params": {
        "lyraDeviceId": "7677C1FD",
        "deviceId": "v1:4:pc_74156cfc...5bd",
        "displayName": "MINGSVATX",
        "A2ANotifyFwd": 1          ← 通知流转能力位
      }}]},
  "skills": [{"id":"office","name":"办公", ...}]
}
```

`A2ANotifyFwd: 1` 是「我能接收通知转发」的声明位。手机据此判断目标是否可用。

## 五、配置链路

### 5.1 入口是对话，不是设置页

```java
ManageNotificationTool implements Tool
  ACTION_QUERY_RULES = "query_rules"
  ACTION_SUBSCRIBE   = "subscribe"
  PARAM_ACTION / PARAM_MESSAGE / PARAM_APPS / PARAM_DEVICE
```

`handleSubscribe` 把用户原话交给**内置 LLM** 生成规则：

```
[NotifFwd]generateRules: isFirstOpen=
[NotifFwd]handleSubscribe: LLM result=
[NotifFwd]parse: LLM returned clarify=          ← 需要澄清时反问
[NotifFwd]resolveTarget: chosen idx=..., name=..., deviceId=..., continuityId=...,
                        isOnline=..., continuity=...
```

目标设备同样由 LLM 从设备清单里挑选（`resolveTarget`），支持自然语言指代。这是「PC 端无独立配置页」的原因——所有配置都在手机侧对话中完成。

> ✅ 复核确认（用户）：PC 端在配置通知流转时不会出现可见弹窗，也没有独立配置页。

### 5.2 授权在**手机端**弹窗（v3 更正）

```java
// ensureForwardPermission
boolean ok = permissionManager.requestLocalConsent(
        action,                                    // "是否允许通知转发"
        details,                                   // 含 deviceRef.getDeviceName()
        agentId, "", null, null, null,
        positive, negative, false, ...);

// 用户同意后，同一台手机上执行：
notificationListenerGranter.grant("com.aios.osbot.im.service.notification.NotificationForwardListener");
permissionStore.grant(deviceRef);
```

`requestLocalConsent` 的 **Local** 明确指本机弹窗，弹窗文案带目标设备名。

授予通知使用权用反射调隐藏 API（需 `MANAGE_NOTIFICATION_LISTENERS`，小爱是 `/product/priv-app/VoiceAssistAndroidT` 特权应用；当前生效版本在 `/data/app`，`PRIVATE_FLAG_PRIVILEGED` 仍为真，故可行）：

```java

    "setNotificationListenerAccessGranted", ComponentName.class, boolean.class)
```

**PC 端无感知，无弹窗。**

⚠️ v2 曾写成「PC 端弹窗由用户点同意」，错误。混淆点在于另一个方法：

## 六、数据落地

### 6.1 规则文件

`/data/user/0/com.miui.voiceassist/files/notification-subscriptions.json`

```json
{"ruleId": "nf_14da45d2",
 "source": {"deviceId": "v1:0:ud:r93P04...", "deviceName": "Xiaomi 17 Ultra by Leica/nezha"},
 "target": {"deviceId": "v1:4:pc_74156cfc...", "deviceName": "MINGSVATX"},
 "filter": {
   "andGroups": [{"branches": [
      [{"field":"app","op":"in","value":"[\"com.tencent.mm\",...]"}],
      [{"field":"app","op":"in","value":"[20个应用]"},
       {"field":"isIsland","op":"is","value":"true"}],
      [{"field":"app","op":"in","value":"[\"com.android.mms\"]"},
       {"field":"isVerifyCode","op":"is","value":"true"}]
   ]}],
   "ruleText": "已开启通知转发到电脑 MINGSVATX：……"
 },
 "meta": {"createdAt": 1794322764062, "updatedAt": 1794322764062}}
```

**规则 DSL**：`andGroups`（组间 AND）→ `branches`（分支间 OR）→ 条件（组内 AND）。

| 字段 | 操作符 | 语义 |
|---|---|---|
| `app` | `in` / `not_in` | 包名集合 |
| `isIsland` | `is` | 是否焦点通知（值 `true` / `false`） |
| `isVerifyCode` | `is` | 是否验证码（值 `true` / `false`） |
| `sender` | `regex` / `not_regex` | 发送者正则 |
| `text` | `regex` / `not_regex` | 文本正则 |

> 📄代码：`NotificationForwardRuleGuard` 只接受上述组合；`regex/not_regex` 不适用于 `app`、`isIsland`、`isVerifyCode`。

### 7.2 五道闸门

| # | 闸门 | 判定 | 日志 |
|---|---|---|---|
| 1 | 屏蔽应用 | `android` / `com.android.incallui` / `com.android.server.telecom` / `com.android.systemui` / `com.milink.service` / `com.miui.bugreport` / `com.xiaomi.mi_connect_service` | `forced blocked app` |

```java
// 闸门4 的实现
public final String targetSkipReason(String targetId, Integer importance, Boolean enableFloat) {
    if (isDesktopTarget(targetId) && !(importance != null && importance >= 4 && Boolean.TRUE.equals(enableFloat)))
        return "desktop target non-important notification";
    return null;
}
```

> ⚠️ **「全部通知」不等于所有通知**。低优先级通知会被闸门 4 挡掉。日志中 `nf_5a02917d`（写「全部通知」）仍频繁 `skip` 即为此故。

> 闸门 1 的清单至少包含 `android`；文档 v3.0 遗漏。其余包是否完整仍需完整反编译确认。
>
> `isDesktopTarget` 是文档中的语义名；DEX 未出现同名字面量，实际方法名可能被混淆。

| 事件名 | 方向 | 处理器 | 作用 |

### 是否全部走 A2A？

**主链路是，但不绝对**：

- 通知投递、点击回传、授权提示、图标获取 → 均在 A2A 事件框架内（`com.aios.osbot.interconnect.*`）
- A2A 本身是**逻辑层**，底下可落到 Continuity 直连 / PubSub 云 / miTalk / HTTP 任一种
- `device.notification` 走的是接收侧内部 PubSub，不是 A2A topic
- 设备发现与 Profile 同步走 Continuity 静态 topic `assistantA2a`（属 A2A 传输层）

一句话：**A2A 是消息格式与路由约定，不是物理通道。**

## 十、边界行为（✅实测/📄代码）

| 行为 | 实现 | 影响 |
|---|---|---|
| **删除不同步** | `onNotificationRemoved()` 空实现 | 手机划掉通知，PC 端那条仍在 |
| **冷启动丢通知** | `a==null` 或 `b==null` 直接 return | 进程刚起时的通知被丢弃，不补发 |
| **不可达即放弃** | `channels==2` 且不可达 → return | 无队列、无重试、无降级 |
| **桌面端重要度** | `importance<4` 或 `enableFloat≠true` → skip | 「全部通知」实为「重要通知」 |
| **未发现发送历史文件** | 持久化规则与授权；未发现专门的转发历史 | 无法事后审计，只能实时抓 logcat |
| **1 MB 上限** | 超限丢弃 | 超大正文通知丢失 |

## 十六、面向 LSPosed 设置面板的实现结论（2026-11-11）

- 面板形态：通过 LSPosed 注入 `com.miui.voiceassist` 进程，直接操作同一 Dagger 作用域内的 `NotificationSubscriptionStore`，不采用普通应用直接读写 `/data/user/0` 的方案。
- 规则读取：`getAllRules()` 取全部；`getActiveRules(sourceDeviceId)` 取某来源的 active 规则。
- 规则写入：`setRule(source, target, filter)` 按 `(sourceDeviceId, targetDeviceId)` upsert，内部 `synchronized` + `.tmp` rename 原子落盘；`removeRule(ruleId)` 按规则删除；`deleteByTarget(source, target)` 删除目标下全部规则。
- 加载语义：store 在构造时一次性 `loadFromDisk()`，没有 FileObserver/reload。不要直接改 JSON 后期待运行中的监听器立即生效；应调用同一 store 实例的公开方法。JSON 解析失败会被当作空列表，直接改文件风险很高。
- 权限语义：`ensureForwardPermission` 在配置阶段检查系统通知监听授权与 `permissionStore.isGranted()`；`NotificationForwardListener` 在发送阶段不再查 `permissionStore`。面板仍应显式确认，并同步 `permissionStore.grant/revoke`，避免查询结果与规则状态不一致。
- 目标设备：`deviceService.getDeviceList()` 返回设备及 `isOnline` / `mitalkOnline` / `continuityReachable`；`DeviceProfileManager.notifyForwardVersion >= 1` 判定接收能力。接收端仅允许 `PC` / `PAD` / `MAC`，手机被明确拒绝。
- 规则校验：`NotificationForwardRuleGuard` 只接受 `app in/not_in`、`isIsland is bool`、`isVerifyCode is bool`、`sender/text regex/not_regex`；面板应在写入前复用该校验。
- 通知删除：`onNotificationRemoved()` 为空实现，手机侧删除不会同步到对端。
- PC 接收端（用户确认，暂不展开）：PC 超级小爱发送 Windows 原生通知；点击后拉起小米电脑管家投屏，将源应用投屏到 PC。
- 范围：上述 PC 接收端行为与平板实机适配本轮不纳入。

*v3.1 由本机 root 探查 + 超级小爱 APK 定点反编译 + logcat 交叉核对整理。标 ❓ 者无本地证据，不予推测。*
